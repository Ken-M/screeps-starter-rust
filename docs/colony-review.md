## 5. 現在の設計

### 判断のレイヤー
- **ロール**: miner（source 固定・WORK5上限）/ hauler（CARRY:MOVE 1:1、満載⇄空のステートマシン、減衰物優先回収）/ worker（downgrade救援 > duty 1体 > **パリティ半数が upgrade** > 建設 > 修理 > 暇なら upgrade）/ defender（敵検知時のみ、rampart 陣地戦）
- **目標**: creep 総数比ではなくコロニー構造の関数（source数・敵の有無・施設）+ 滞留エネルギー連動の worker 増員
- **先行生産**: miner の残寿命 250 tick で後継を生産、同じ source を引き継ぐ
- **緊急モード**: 人口<4 または miner/hauler がゼロ → 今あるエネルギーで即時生産
- **防衛**: セーフモードは「重要建造物HPの実減少×武装敵」のANDでのみ。タワーは実効ダメージ+ヒーラー優先。防衛 rampart は封鎖検証つき反復配置
- **修理**: Rampart/Wall は RCL 連動の目標 HP で頭打ち（修理労働の吸い込み防止）
- **建設**: 20tickごとに RCL 上限との差分を自動配置（container=source脇、拠点=市松、防衛=封鎖、道路=沼のみ）

### 手段のレイヤー
- tick キャッシュ（建造物・敵・地形・仕事サマリ・コロニー観測・部屋RCL）、静的/動的コスト層、move_by_path、Memory キーは `mem::keys` に集約
- util は cache / pathing / predicates / stats / finders の5モジュール
- **観測**: 100 tick ごとの summary 2行（RCL進捗 / downgrade / エネルギー / 人口 / CPU / bucket）。逐次ログは debug。watch-console 常駐 + 400MB ローテート
- 純粋関数テスト21件（role_targets / build_body / tower減衰 / danger_cost / barrier_target_hp / 封鎖BFS・門検出）

## 6. 防衛評価 — 「攻撃を受けた時に生産と防御は間に合うか」

**結論: 無敵時間は終了したが、タワー稼働 + 侵入経路封鎖 + セーフモード在庫2 で、前回評価から質的に改善。NPC級は自動対処、本気のプレイヤーにも時間稼ぎが成立する。**

### 現在の防衛態勢
| 層 | 内容 |
|---|---|
| 第1層: 封鎖 | 敵視点 BFS で検証済みの rampart 封鎖線。近接敵は重要建造物の隣接マスに立てない（壊すには rampart 30k を削る必要） |
| 第2層: タワー | 1基・応答0tick・威力600（射程5以内）。実効ダメージ標的 + ヒーラー優先。直上 rampart 済み |
| 第3層: defender | 敵検知と同tickで生産開始（攻撃能力持ちの敵のみに反応）。rampart 陣地戦で一方的な間合いを取る |
| 最終層: セーフモード | **在庫2・クールダウンなし**。重要建造物の実被弾で即時自動発動 |

### 脅威別の見立て
- **NPCインベーダー級（1〜2体）**: タワーだけで撃破可能。封鎖線に足止めされている間に defender も間に合う
- **本気のプレイヤー（ATTACK10以上/ヒーラー付き）**: rampart 30k は数十〜百tickで割られるが、その間タワーが削り続け、抜かれてもセーフモード自動発動で20,000 tick の猶予を得る。「即死」は無くなった
- 弱点は**遠隔敵**（封鎖線の外から range3 で miner / container を叩ける）と、rampart 修理が追いつかない持久戦

### 提言（優先順）
1. **RCL4 へ**: storage 解禁で経済が安定し、rampart 修理目標も 30k→100k に自動で上がる（`barrier_target_hp` が RCL 連動）
2. defender 数を敵の攻撃パーツ数に比例させる（現在は固定2）
3. 敵入室時に非戦闘 creep を封鎖線の内側へ退避させる（現在は danger コストによる経路回避のみ）
4. 封鎖線の門の内側 range3 に tower を増設する配置規則（RCL5 で2基目解禁）

## 7. 刷新時に発生し修正した回帰（教訓）

| 回帰 | 症状 | 原因と修正 |
|---|---|---|
| ロスター化前の重複読み | creeps 4.5→7.4 CPU | body/Memory を tick 内で複数回読み直し → 1回読みのロスター化 |
| スタック過敏判定 | CPU倍増 | 正常渋滞を誤検知し毎tickフル再探索 → 閾値5+カウンタリセット（後に退役で機構ごと削除） |
| upgrade係が粘着しない | downgrade進行 | 「毎tick先頭のworker」指名が移ろい誰も到着しない → Memoryフラグで固定 |
| worker のエネルギー欠落 | 全workerが立ち尽くす | 退役時に採取フェーズの代替を用意し忘れ → hauler の調達ロジックを共有化 |
| hauler 全滅デッドロック | 人口11→4、生産停止 | hauler ゼロ→補給されず実質上限300 < hauler 設計コスト400 → 緊急モードで即時生産 |
| **RCL3到達で upgrade 停止**（第2波#4） | progress 1.1/tick | 傾斜の RCL3 未満限定が「到達したら切れる」ことを意味していた → 恒久化 |
| **誘導するのに引き出せない**（第2波#5） | 墓標の隣で立ち往生 | 経路目標と隣接アクションの対応漏れ → 対で実装・対で確認する |

いずれもログ常駐+summary の観測基盤が実測で捕捉した。第2波はこの基盤自体の改善（#2）が起点になっており、**観測→検出→修正→実測確認のループが1日で6件回る**ことを確認した。「デプロイ後 N tick の自動ベンチ比較」をスクリプト化すれば検知が人手不要になる（未実装・推奨）。

## 8. 残課題

- **PathFinder 系 CPU**（worker 増で再燃しうる）: tick 単位の CostMatrix キャッシュ、`empty_search` の廃止（候補ゼロ確認に本物の探索を使っている）、hauler 配達 fallback の最大8探索
- **spawn の body 小型化**: 平均 523 energy で出しており、再生産に収入の26%を消費。エネルギー貯蓄を待って大型 body を出す方針の検討
- **market が実質 no-op**: credits が20時間不変。RCL3 では売る物が無いのが実態（terminal は RCL6）。それまで実行間隔を落とす程度で可
- **道路網が0本**: 「沼のみ」規則で候補が無い。幹線（spawn⇄source⇄controller）の平地舗装を解禁すれば hauler/worker の MOVE 比率を下げられる（封鎖完了で計画予算は空いた）
- 鉱物採取の再実装（RCL6 の Extractor 解禁まで猶予あり）
- controller 側の物流（container + hauler ルート）— アップグレード throughput の本命
- リンクのペア配置規則（source脇⇄ハブ。RCL5まで猶予）
- find_nearest_* の共通化 / TOUGH 導入 / デプロイ後自動ベンチ
- 複数部屋展開（storage 稼働後）
