## 4b. 第3波 — 専任 upgrader 実験・壊滅・復旧（2026-08-24〜26）

29コミット。**うち11件は自分が入れた変更が招いた回帰の後始末**で、最終的に
コロニーは一度壊滅し、自律復旧した。以下は経緯そのものが教訓なので順に残す。

### 1. 発端 — 進捗が 1/4 に落ちた

`5b624d5` で専任 upgrader（controller 脇 container の隣に座り WORK 全振り）を
新設した直後から、進捗が 4,000〜6,000/h → 1,100〜1,500/h に低下。ログ解析で3つ判明。

| 症状 | 原因 |
|---|---|
| `rebalance worker→upgrader` が 553 回 / `none:1` が常時 | 退役ロール一覧に `"upgrader"` が残っていた。現役復帰させた際の外し忘れで、毎 tick 全 upgrader の ROLE が削除されていた |
| backlog が 4k→15k に発散 | hauler 目標が固定のまま消費側（upgrader/worker）だけ滞留連動で増える構造 |
| 補給 container に一度も届かない | 配達が spawn/tower/extension の全充足後だったため、生産が回る間は永久に後回し |

→ 退役一覧の修正、`surplus_haulers` の新設、配達優先順の見直しで対処（`2589579` ほか）。

### 2. ベンチが回帰を見逃していた

当時の `bench.js` は3区間（約19分）を比較しており、「✅ 回帰なし」と誤判定していた。
creep 寿命 1,500 tick（約90分）で人口が入れ替わるため、19分では新ロジックの定常状態に
達しない。**settle 窓**（既定8区間＝約50分読み飛ばし）と backlog 倍増の検知を追加（`519df27`）。

さらに後日、`progress 2.12 → 0.00` を「✅ 回帰なし」と報告する欠陥が判明。
`beforeRate && afterRate` は `afterRate === 0` が falsy で弾かれ、**進捗完全停止という
最悪の事態だけ検知できない**。before 側のみ存在確認する形に修正（`c7c43cf`）。

### 3. 席の導入と、それが招いた物流停止

upgrader 同士が container 周りで押し合うため、miner の `MINE_AT` と同じ粘着方式で
**指定席**（`UPGRADE_SEAT`）を導入（`7ecc33f`）。同時に、着席 creep を経路上
**通行不可（0xff）** にした。ここから連鎖が始まる。

| # | 変更 | 招いた結果 |
|---|---|---|
| 1 | 着席 creep を 0xff に | 席が container の歩けるマス4つを全部塞ぎ、hauler が搬入不能に |
| 2 | 搬入レーンを確保（`f3cfcf3`） | 経路がゴール近傍を迂回するため探索コストが膨張 |
| 3 | `max_ops` が 500 のまま | ゲーム内 PathFinder で実測 **825 ops 必要** → `incomplete` で hauler が配送を全部諦め、**進捗が完全凍結** |

→ `max_ops` をエンジン既定の 2,000 に復元（`2050d75`）。「到達できる探索は必要分しか
消費しない」ので、CPU 最適化のつもりの絞り込みが逆に機能停止を招いていた。

### 4. 地形が全ての答えだった

部屋を全面マップして判明: **spawn/source 側と controller は岩壁で完全に分断され、
唯一の通路は西回り約60〜80歩の大迂回路**。東からの近道は存在しない（恒久地形）。

これで一連の観測がすべて説明できた。
- 遠くで「うろうろ」して見えた creep 群 = 西回り幹線の通勤者
- 配送経路が80歩・825 ops = 正しい最短路がそれしかない
- stock が常に枯渇 = 補給1往復に 120〜160 tick かかる

### 5. invader 4体による壊滅と自律復旧

物流が弱った状態で NPC invader 4体（TOUGH2 + HEAL5×2 を含む隊）の襲撃を受け、
**経済 creep 全滅・tower 0・進捗完全停止**に至った。直接の引き金は2つ。

1. **タワーの無駄撃ち**: 射程37〜41の敵を67発撃って 1000→0 に枯渇。距離20超の威力150では
   敵チームの回復力（HEAL10個＝120/tick）を超えられず一切削れない。標的選択は減衰を
   考慮していたが「**そもそも撃つ価値があるか**」を見ていなかった
2. **tower への補給が構造的にゼロ**: 「stock が枯れかけなら割り込む」を tower より前に
   置いていたため、stock は upgrader が消費し続けて常に枯れ気味 → 割り込みが恒久的に
   成立し、tower には一度も届いていなかった

復旧のために入れた対策も、それぞれ次の詰まりを生んだ（いずれも実測で特定・解消）。

| 対策 | 次に起きたこと |
|---|---|
| 経済壊滅時は defender を作らない（`60e13c4`） | — |
| 復旧は運搬から（`fdaaefe`） | hauler を3体作り続け miner が立たない → hauler がゼロの間だけに限定（`b1b724c`） |
| 籠城貯金（`6a93c9a`） | 目標550が spawn 容量300を超えて到達不能 → 300に修正（`58ab568`） |
| tower を spawn の次に（`6014fc1`） | tower 容量1000を埋め切るまで extension が飢える → 迎撃分300で譲る（`c790a73`） |

**結果**: セーフモードを使わずに約70分で自律復旧。rampart が invader の寿命より長く
持つと実測で見極め、在庫2個を温存できた。

### 6. 専任 upgrader からの撤退

復旧後も進捗は 840/h に留まった。導入前後を実測比較すると差は決定的だった。

| 方式 | 進捗 |
|---|---|
| worker 主体（08-23 16〜22時） | **3,377〜6,093/h** |
| 専任 upgrader 主体（08-25） | 0〜1,623/h |

**約6分の1**。専任 upgrader は「controller が近い部屋」を前提とした設計で、
大迂回路のこの部屋では hauler が stock まで届かず成立しない。優先順をどう入れ替えても
「どこかが飢える」のは、輸送力が構造的に足りないため。

→ ロールは残したまま、**目標数を補給 container の実在庫で決める**形にした（`009d3ab`）。

```
在庫 ÷ 840（1体が hauler 一往復 ≒140tick を凌ぐ量）
  在庫ゼロ → 専任 0、worker の半数が upgrade を担う
  在庫潤沢 → 専任が自動復活
```

あわせて worker 側の「半数を upgrade に回す」傾斜の判定を、`has_controller_stock`
（container の**有無**）から `upgrader_target() == 0`（専任が**立っているか**）に変更
（`8fa203b`）。container はあるが補給が届かず専任0、という状態で
**どちらの担い手も upgrade しない空白**が生じていた。

**実測**: 修正後19分で +2,147（約6,800/h 相当）。導入前の健全期を上回る水準に回復。

### 7. 交通管理（swap プロトコル）

「一本道で対向とぶつかると道路から降りて迂回する」問題に対し、移動を
**即時発行 → 意図の登録 + tick 末の一括解決**に変える設計を `docs/traffic-design.md`
に起こし、Phase 1（配管化・挙動不変）と Phase 2（解決器）を実装した。

- 優先度降順にチェーン追跡し、**隊列 / swap・循環は許可**、遊休 creep は深さ1の
  **押し出し**、着席・硬直・敵は却下して 1 tick 待つ
- 中核 `resolve_intents` は game API 非依存の純ロジックで、単体テスト11件
- 副産物として、コスト層に tick 内キャッシュが入り CPU が -8%

Phase 3（道路上の味方コストを下げて直進すれ違いを促す）は**未実施**。当初の問題は
未解決のまま残っている（§8）。

### 10. 教訓

1. **観測できないものは直せない**。「upgrader が遊んでいる」「rampart が痩せている」は
   どれも summary ログには出ず、API 直読みで初めて見えた
2. **局所的な優先順位の入れ替えは連鎖する**。tower を上げれば extension が飢え、
   stock を上げれば tower が飢えた。順位ではなく**総量（輸送力）が足りない**のが
   本質だったが、そこに至るまで4回入れ替えた
3. **リソース上限は「到達可能か」を確かめる**。籠城貯金550 も max_ops 500 も、
   実際には到達・充足しない値で、機能を静かに殺していた
4. **前提が変わったら、それに依存した仕組みを消す**。stock 割り込みは「upgrader が
   自力調達に出る」前提の対策で、「席で待つ」に変えた時点で役目を終えていたのに
   残り続け、壊滅の引き金になった
5. **設計は部屋の地形に従属する**。専任 upgrader の成否は controller までの距離で決まる。
   固定の判断ではなく実測値（在庫）で自動切り替えするのが正解だった

## 5. 現在の設計

### 判断のレイヤー
- **ロール**: miner（source 固定・WORK5上限）/ hauler（CARRY:MOVE 1:1、満載⇄空のステートマシン、減衰物優先回収）/ worker（downgrade救援 > duty 1体 > **専任が0なら半数が upgrade** > 建設 > 修理 > 暇なら upgrade）/ upgrader（**補給在庫が足りる分だけ**・指定席・空荷でも席で待つ）/ defender（敵検知時のみ、rampart 陣地戦）
- **配達優先順**: spawn（生産の要）→ tower（迎撃分300まで）→ extension → 補給 container → tower（満タンまで）→ storage。各段は「満ちたら次へ」で、どこか1つが独占しないようにする（§4b-5）
- **目標**: creep 総数比ではなくコロニー構造の関数（source数・敵の有無・施設）+ 滞留エネルギー連動の worker 増員
- **先行生産**: miner の残寿命 250 tick で後継を生産、同じ source を引き継ぐ
- **緊急モード**: 人口<4 または miner/hauler がゼロ → 今あるエネルギーで即時生産。ただし敵がいる間は**籠城貯金**（spawn 容量300まで貯めてから厚い body を出す）
- **復旧順**: 経済壊滅時は defender を作らず、滞留在庫があれば hauler を最優先（hauler がゼロの間だけ）→ 以降は通常の miner 優先に戻る
- **防衛**: セーフモードは「重要建造物HPの実減少×武装敵」のANDでのみ。タワーは実効ダメージ+ヒーラー優先に加え、**実効ダメージが敵チームの回復量を超えないうちは撃たない**（温存が防衛力になる）。防衛 rampart は封鎖検証つき反復配置
- **修理**: Rampart/Wall は RCL 連動の目標 HP で頭打ち（修理労働の吸い込み防止）。対象は `REPAIR_AT` で粘着し、閾値+30k まで直し切ってから離れる（標的が移る往復行軍の防止）
- **建設**: 20tickごとに RCL 上限との差分を自動配置（container=source脇、拠点=市松、防衛=封鎖、道路=spawn⇄source⇄controller⇄**補給container**の幹線を平地含めて舗装）

### 手段のレイヤー
- tick キャッシュ（建造物・敵・地形・仕事サマリ・コロニー観測・部屋RCL・**完成コスト層**）、静的/動的コスト層、Memory キーは `mem::keys` に集約
- **移動は交通管理経由**: 各ロールは `request_move` で意図を登録し、creep_loop 後に `resolve_traffic` が突き合わせて一括発行（隊列 / swap / 押し出し / 優先度）。詳細は `docs/traffic-design.md`
- `max_ops` はエンジン既定の 2,000。絞ると到達可能な経路まで `incomplete` になる（§4b-3）
- util は cache / pathing / predicates / stats / finders / **traffic** の6モジュール
- **観測**: 100 tick ごとの summary 2行（RCL進捗 / downgrade / エネルギー / 人口 / CPU / bucket）。逐次ログは debug。watch-console 常駐 + 400MB ローテート
- 純粋関数テスト**44件**（role_targets / build_body / tower減衰 / danger_cost / barrier_target_hp / 封鎖BFS・門検出 / **交通解決器11件** / **復旧順・在庫連動の目標**）
- **診断**: `js_tools/room-snapshot.js` で「今この瞬間の在庫と配置」を API 直読み（§4b-9）

## 6. 防衛評価 — 「攻撃を受けた時に生産と防御は間に合うか」

**結論: NPC invader 4体の襲撃を実戦で2度受け、1度目は壊滅、2度目は無傷で撃退した（§4b-5）。差はタワーにエネルギーが入っていたか否か。**

| | 1度目（08-25 04時） | 2度目（08-25 12時） |
|---|---|---|
| tower | **0**（無駄撃ちで枯渇） | **660/1000** 稼働 |
| 撃った射程 | 37〜41（威力150・回復に相殺され0ダメージ） | **27**（有効） |
| 結果 | 経済 creep 全滅・進捗停止・自律復旧に70分 | invader 0体・spawn/rampart 無傷 |

セーフモードは両方とも未使用（在庫2を温存）。1度目は rampart が invader の寿命より
長く持つと実測で見極めて籠城した。

### 現在の防衛態勢
| 層 | 内容 |
|---|---|
| 第1層: 封鎖 | 敵視点 BFS で検証済みの rampart 封鎖線。近接敵は重要建造物の隣接マスに立てない（壊すには rampart 30k を削る必要） |
| 第2層: タワー | 1基・応答0tick・威力600（射程5以内）。実効ダメージ標的 + ヒーラー優先 + **削れない相手には撃たない**。配達優先順で迎撃分300を常時確保。直上 rampart 済み |
| 第3層: defender | 敵検知と同tickで生産開始（攻撃能力持ちの敵のみに反応）。rampart 陣地戦で一方的な間合いを取る。**経済が壊滅している間は作らない**（収入ゼロで最小 body を逐次投入すると溶けるだけ） |
| 最終層: セーフモード | **在庫2・クールダウンなし**。重要建造物の実被弾で即時自動発動 |

### 脅威別の見立て
- **NPCインベーダー級（1〜2体）**: タワーだけで撃破可能。封鎖線に足止めされている間に defender も間に合う
- **本気のプレイヤー（ATTACK10以上/ヒーラー付き）**: rampart 30k は数十〜百tickで割られるが、その間タワーが削り続け、抜かれてもセーフモード自動発動で20,000 tick の猶予を得る。「即死」は無くなった
- 弱点は**遠隔敵**（封鎖線の外から range3 で miner / container を叩ける）と、rampart 修理が追いつかない持久戦

### 提言（優先順）
1. **RCL4 へ**（残り5%）: storage 解禁で経済が安定し、rampart 修理目標も 30k→100k に自動で上がる（`barrier_target_hp` が RCL 連動）。補給の安定で専任 upgrader が本格的に機能する可能性もある
2. **tower 2基目**（RCL5）: 1基では HEAL 持ちの invader 隊を「撃退」まで持ち込めず、寿命切れ待ちになった
3. defender 数を敵の攻撃パーツ数に比例させる（現在は固定2）
4. 敵入室時に非戦闘 creep を封鎖線の内側へ退避させる（現在は danger コストによる経路回避のみ）

## 7. 刷新時に発生し修正した回帰（教訓）

| 回帰 | 症状 | 原因と修正 |
|---|---|---|
| ロスター化前の重複読み | creeps 4.5→7.4 CPU | body/Memory を tick 内で複数回読み直し → 1回読みのロスター化 |
| スタック過敏判定 | CPU倍増 | 正常渋滞を誤検知し毎tickフル再探索 → 閾値5+カウンタリセット（後に退役で機構ごと削除） |
| upgrade係が粘着しない | downgrade進行 | 「毎tick先頭のworker」指名が移ろい誰も到着しない → Memoryフラグで固定 |
| worker のエネルギー欠落 | 全workerが立ち尽くす | 退役時に採取フェーズの代替を用意し忘れ → hauler の調達ロジックを共有化 |
| hauler 全滅デッドロック | 人口11→4、生産停止 | hauler ゼロ→補給されず実質上限300 < hauler 設計コスト400 → 緊急モードで即時生産 |
| **RCL3到達で upgrade 停止**（第2波#4） | progress 1.1/tick | 傾斜の RCL3 未満限定が「到達したら切れる」ことを意味していた → 恒久化 |
| **誘導するのに引き出せない**（第2波#5） | 墓標の隣で立ち往生 | 経路目標と隣接アクションの対応漏れ → 対で実装・対で確認する |

いずれもログ常駐+summary の観測基盤が実測で捕捉した。第2波はこの基盤自体の改善（#2）が起点になっており、**観測→検出→修正→実測確認のループが1日で6件回る**ことを確認した。「デプロイ後 N tick の自動ベンチ比較」をスクリプト化すれば検知が人手不要になる（未実装・推奨）。

## 8. 残課題

- **交通管理 Phase 3 が未実施**: 当初の課題（一本道で対向とぶつかると道路から降りて迂回し、道路特化 body が倍の tick を払う）は**未解決のまま**。解決器（Phase 2）は入っているので、道路上の味方コストを 8→2 に下げれば直進すれ違いが成立するはず。`docs/traffic-design.md` §6 参照
- **輸送力が構造的に不足**: 大迂回路のため hauler 1体の実効輸送は 2.5〜3.3/tick。産出 20/tick に対し上限を source×2 まで上げたが、backlog は 8k 前後で高止まりし、地面の落下分が毎tick 蒸発している。storage 解禁後に中継拠点を置く設計が本命
- **PathFinder 系 CPU**: 完成コスト層の tick 内キャッシュは入れた。残りは `empty_search` の廃止（候補ゼロ確認に本物の探索を使っている）、hauler 配達 fallback の探索数
- **market が実質 no-op**: credits が不変。RCL3 では売る物が無いのが実態（terminal は RCL6）
- 鉱物採取の再実装（RCL6 の Extractor 解禁まで猶予あり）
- リンクのペア配置規則（source脇⇄ハブ。RCL5まで猶予）
- find_nearest_* の共通化 / 複数部屋展開（storage 稼働後）
